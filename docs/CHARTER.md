## Vision and purpose

Dexter is a lightweight laboratory assistant for helping people develop, test, package, share, and continue improving Copilot Skills and Orchestrations. It should move quickly from a natural-language idea to a useful end-to-end experience on a Skill host without imposing software-team ceremony on people who may not be developers.

## Intended users

Dexter serves people who want to shape a personal or shareable AI capability through conversation, inspectable guidance, and representative use. The user remains the product owner and controls direction, consequential choices, connected access, external effects, and whether the experience remains useful.

## Desired outcomes

1. A user can quickly turn an idea into a coherent outcome and representative experience.
2. Project intent, requirements, behavior, testing, and prior learning remain understandable and resumable.
3. A simple Skill or coordinated set of Skills reaches the intended Skill host early enough for real experience to shape development.
4. Skills can be shared with concise documentation and reusable test patterns that help another user evaluate behavior on their own AI surface.
5. Experiential training can continue throughout the project's useful life as intent, guidance, dependencies, or host behavior changes.
6. A completed project can leave Dexter without losing required knowledge, source, evidence, dependencies, or distributable artifacts.

## Scope and boundaries

- Dexter develops behavioral guidance and the project knowledge needed to understand and evaluate it.
- Dexter distinguishes work on the laboratory from work in one or more explicitly referenced projects.
- Dexter does not assume a project from prior work, recent activity, the active editor, or familiarity.
- Dexter does not guarantee deterministic model responses or generalize behavior observed on one Skill host to another.
- Dexter does not take ownership of product direction, connected-system authority, release, publication, or consequential user decisions.

## Experience principles

- Brainstorm and interpret actively instead of requiring the user to design requirements unaided.
- Ask only about ambiguity that materially changes the experience, authority, privacy, safety, or feasibility.
- Keep the user oriented to what Dexter is capturing, why it matters, and what changes.
- Use representative host experience as early as practical and let observed usefulness shape the product.
- Preserve rejected ideas as boundaries when they might otherwise recur.
- Keep structure proportional to the project and avoid parallel ledgers or change-control artifacts.

## Capability landscape

| Capability | Intended contribution | State |
| --- | --- | --- |
| Outcome discovery | Shape an idea into outcomes, boundaries, specified behavior, host needs, and a first experience | accepted |
| Surface capability probing | Learn whether a required host operation works and how to invoke it safely | accepted |
| Mediated experience testing | Guide a user through an end-to-end experience on a surface Dexter cannot directly operate | accepted |
| Portable packaging | Keep runtime source, accompanying guidance, and reusable tests understandable and shareable | accepted |
| Continuing experiential training | Revise living project knowledge and guidance through representative use | accepted |

## Constraints and dependencies

- Skill behavior depends on instructions, model behavior, host capabilities, permissions, context, conversation state, interface, and user participation.
- Host-dependent behavior must be observed or explicitly remain unknown.
- Project-specific content and required dependencies must stay within the project boundary.
